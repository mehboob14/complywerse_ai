1. Governance

7 sub-modules · 14+ link tables · 4 AI surfaces

1.1 Governance Objectives & Strategic Alignment

Strategic direction tracking with cross-domain impact analysis.
  • CRUD on GovernanceObjective. name, description, owner, status, target_date.
  • Tracks alignment of operational activity against board-set objectives.
  • Dashboard aggregates objectives + exceptions by status; flags overdue + pending approvals.
RiskGovernanceLink IssueGovernanceLink DocumentRiskLink

1.2 Document Management (Policies, Procedures, Standards)

Full lifecycle, immutable versions, multi-step approval chains, annotations.
  • Lifecycle states: draft → pending_review → pending_approval → approved → published → expired → archived.
  • Versioning: GovernanceDocumentVersion with change_type (major/minor/patch), change_summary, approval history.
  • Multi-step approval: DocumentApprovalStep with sequence, approval_type (single/any/all), delegations, due dates.
  • Reviewers: DocumentReviewer with owner/author/reviewer/approver/stakeholder roles + notification prefs.
  • Audit trail: DocumentAuditLog tracks every field-level change with diff.
  • Collaborative review: DocumentAnnotation for inline comments at text-range or general level.
  • Policy review cycles: PolicyReviewHistory records periodic / ad-hoc / triggered reviews.
AI: policy auto-classify AI: section extraction DocumentControlLink DocumentAssetLink DocumentRegulatoryLink DocumentRiskLink

1.3 Policy Exceptions Management

Formal acceptance of risk against published policy, with AI-drafted justification.
  • PolicyException with priority, effective/expiry dates, risk assessment, compensating controls.
  • AI suggestion endpoint: POST /policy-exceptions/suggest-content. uses OpenAI/Claude to draft justification + risk assessment + compensating controls from policy context (≤3500 char excerpt).
  • Lifecycle: draft → pending_approval → approved / rejected / revoked.
  • Threaded discussion via PolicyExceptionComment.
  • Expiry tracking with automatic re-review reminders; when exception expires, dependent risks revert to "unmitigated".
AI: OpenAI exception draft PolicyException → GovernanceDocument

1.4 Attestation & Certification Campaigns

Periodic user sign-offs on policies, with multi-tier escalation chains.
  • Campaign types: sox_302, sox_404, policy_signoff, bcp_awareness, training_acknowledgment.
  • Audience targeting: all_users, by_department, by_role, custom.
  • Per-request tracking: AttestationRequest with reminder_sent_at, escalation_sent_at.
  • Escalation chains: EscalationChain defines 4 tiers (staff → manager → director → CRO) with delay periods.
  • Optional evidence attachment per attestation for compliance proof.

1.5 Board & Committee Management

Charters, meetings, agendas, voting, minutes. all auditable.
  • Committee types: board, risk_committee, audit_committee, compliance_committee, it_steering, custom.
  • Membership: CommitteeMember with role (chair/secretary/member/observer), joined_at, left_at.
  • Charter management: CommitteeCharter with versioning, effective/expiry dates, structured sections_json (supports both AI-generated and uploaded charters).
  • Meetings: CommitteeMeeting with quorum tracking, virtual_link, status state machine.
  • Agenda items: MeetingAgendaItem (approval / discussion / information / action_review) with linked document / risk / regulatory_change, time_allocated, outcome.
  • Per-member voting: MeetingAgendaItemVote tracks consensus (agreed / disagreed / partial / abstain) with comments.
  • Minutes: MeetingMinutes one-to-one with meeting.
  • Oversight actions: OversightAction ties committee decisions to Issue tracking.
AI: meeting transcript → minutes AI: charter generator

1.6 Regulatory Change Management

Automated regulatory intelligence pulled from RSS feeds, with impact mapping to policies + risks + controls.
  • RegulatoryChange tracks framework changes, applicability, impact assessment.
  • RSS ingestion: RSSFeedSource + RSSFeedItem for automated regulatory intelligence feeds.
  • Impact mapping field impact_risk_ids (JSON array) links directly to risks affected by the change.
  • Committee linkage: MeetingAgendaItem.linked_regulatory_change_id brings changes into committee oversight.

1.7 Policy Gap Analysis

Cross-framework gap detection between policy statements and regulatory requirements.
  • Per-framework gap reports via PolicyGapAnalysisByFramework.
  • PolicyGapFinding ties gaps to regulatory clauses + affected controls + suggested remediation.
  • Findings can promote directly to risk register (auto-create Risk with source_type = "framework_gap").

2. Enterprise Risk Management (ERM)

10 sub-modules · 10+ link tables · RCSA + KRI + Cascade + Appetite

2.1 Risk Register (Core)

  • Risk taxonomy: category (strategic / operational / financial / compliance / technology / third_party / project_change), risk_sub_category.
  • Dual scoring: inherent (likelihood × impact, both 1 to 5) and residual (post-mitigation).
  • Lifecycle: open → mitigating → mitigated → accepted → closed; closure_status (pending_closure / closed).
  • Provenance tracking: source_type. manual / register_import / assessment / incident / rcsa / framework_gap / ubl_import / nca_import.
  • Risk appetite alignment: appetite field + breach detection.
  • Excel import: smart header detection, flexible field mapping, category inference from threat / vulnerability / title.
  • Heatmap: 2D likelihood × impact visualisation with counts per intersection.

2.2 Risk Assessment & Scoring

  • /assess endpoint computes inherent + residual scores (L × I).
  • /treatment captures mitigation narrative + sets status to "mitigating".
  • Score history: RiskScoreHistory logs every change with change_reason + changed_by.
  • Trend analysis: /trends shows score_change vs initial; trend_direction (stable / increasing / decreasing).

2.3 Key Risk Indicators (KRIs)

  • Metric types: numeric / percentage / count / boolean.
  • Threshold tiers: green / amber / red with threshold_direction (lower_is_better or higher_is_better).
  • Measurement frequency: daily / weekly / monthly / quarterly.
  • Historical data: RiskKRIMeasurement records values + status + audit trail.
  • Trend endpoint returns last N days for charting; alerts endpoint surfaces red/amber KRIs platform-wide.

2.4 Risk Incidents & Realization Tracking

  • RiskIncident with incident_date / discovered_date, severity, status, financial_impact (USD), operational_impact.
  • Root cause + lessons learned captured as structured fields.
  • Bidirectional linkage to risks (incident.risk_id ↔ Risk.source_incident_id) so realized risks can be traced.
  • Average resolution time computed from resolved_at − discovered_date.

2.5 Risk Review & Approval Workflow

  • RiskReview with cycle (monthly / quarterly / semi_annual / annual), review_type (periodic / triggered / adhoc).
  • Score delta tracking: previous vs new inherent + residual scores.
  • Reviewer + Approver roles distinct; findings + approval_notes fields.
  • Bulk scheduling endpoint assigns reviews across many risks for quarterly cycles.

2.6 Risk Dependencies & Cascade Analysis

  • RiskDependency with dependency_type (causes / aggravates / mitigates / related) + impact_factor.
  • Cascade compute: /dependencies/{risk_id}/cascade recursively traverses downstream risks (max depth 10, cycle-safe).
  • Cascade score = target_score × impact_factor per level; total_cascade_score sums tree.

2.7 Risk Appetite & Breach Management

  • RiskAppetiteConfig per tenant/category with appetite_level (averse / minimal / cautious / moderate / open / hungry).
  • /appetite/breaches lists risks exceeding category thresholds, sorted by breach_amount.
  • Per-category escalation owners route alerts automatically.

2.8 Risk Mitigation Actions & Evidence

  • RiskMitigationAction with action_type (mitigate / transfer / avoid / accept), priority, expected_residual_reduction, actual_residual_reduction.
  • Many-to-many evidence: RiskMitigationActionEvidence pivot (mirrors InternalControl pattern).

2.9 RCSA. Risk and Control Self-Assessment

  • RCSAQuestion with ai_suggestion_enabled flag.
  • RCSAResponse stores ai_suggestion + ai_suggestion_accepted boolean (tracks whether assessor used the AI hint).
  • AI gap detection: ai_gap_detected + ai_gap_description; aggregate ai_gaps_identified counter on RCSAAssessment.
  • Quality scoring: ai_quality_score (0 to 100) rates response completeness; ai_suggestions_used counter tracks adoption.
AI: question hints AI: gap detection AI: quality score

2.10 Compliance Framework Assessments (Bridge to Compliance Module)

  • Launch an assessment against any of 28 frameworks; workbook auto-populates with every applicable control.
  • Per control: implementation_status (Not / Partial / Implemented / Tested), effectiveness_rating (1 to 5), evidence attachments, internal control mapping, owner + reviewer + sign-off.
  • Readiness % per framework, unmapped controls list, insufficient-evidence flag, failing-test view.
  • Multi-tier approval workflow with AssessmentEvidenceApprovalTier.

2.11 Advanced Reporting & Executive Dashboards

  • Executive dashboard: total_risks, risks_by_category/status/score_band, top_risks (top 10), kri_alerts, pending/overdue reviews.
  • Board summary: executive_summary, appetite_status per category, top 5 risks, key_changes, recommendations.
  • Department summary: per-business-unit risk roll-up.
  • Audit export: JSON dump of risks + incidents + reviews + appetite for compliance reviews.
  • COSO ERM wheel: Strategy / Operations / Reporting / Compliance categories visualisation.

3. Compliance & Frameworks

8 sub-modules · 28 pre-seeded frameworks · NCA Saudi support
28 pre-seeded frameworks. ISO 27001:2022, ISO 22301, ISO 42001, NIST CSF 2.0, NIST 800-53, PCI DSS v4, CIS Controls v8 (+ all CIS OS benchmarks), COBIT, SOC 2, HITRUST CSF, GDPR, NIS2, DORA, SOX, HIPAA, SAMA CSF, Aramco CCC, SABIC CyberTrust, ADHICS, DOH ADHIE, QCB Technology Risks, MAS TRM, SL CSF, SBP ETGRMF, SBP Cloud, SBP Internet Banking, SWIFT CSCF.

3.1 Framework Library

  • Hierarchy: Framework → Domain → ControlObjective → FrameworkControl → FrameworkSubControl.
  • Each control has statement, implementation_guidance, testing_guidance, evidence_requirements baked in.
  • Lifecycle: draft → text_extracted → classifying → classified → parsed → published → completed.
  • Mandatory flag (locks framework against deletion). Per-region tags. Custom frameworks supported via parsing pipeline.

3.2 Normalized Control Library

  • NormalizedControl deduplicates equivalent controls across frameworks (immutable code, maturity_level 0 to 5).
  • ControlMapping bridges NormalizedControl ↔ FrameworkControl (type: direct / partial / related).
  • GRCRequiredEvidence defines evidence types + validation criteria per control.
  • Reverse lookup: given a framework control, resolve normalized equivalent + all sibling framework mappings.

3.3 Compliance Assessments & Approval Workflow

  • ComplianceAssessmentDocument lifecycle: draft → submitted → in_approval → approved / rejected.
  • Multi-tier approval: AssessmentEvidenceApprovalTier with tier_order, approver_type (role / user), auto_approve_days, delegation.
  • Per-item evidence linkage with current_tier tracking and full audit trail.
  • AI evidence recommendations per item (EVIDENCE_RECOMMENDATION_PROMPT via OpenAI/Claude).
  • DCC compliance assessment (66 DCC-1:2022 controls auto-seeded with AI recommendations).
AI: evidence recommendations AI: DCC seeding

3.4 Policy Statement Compliance

  • PolicyStatement categories: security / privacy / operational / financial / regulatory / governance.
  • Compliance states: compliant / partially_compliant / non_compliant / not_assessed / not_applicable.
  • Dashboard rolls up status counts per policy type.

3.5 Certification Journey (v2)

  • Framework selection → certification roadmap auto-populated with control checklist.
  • Per-control implementation status (not_started / in_progress / implemented / verified).
  • Evidence bundling: upload many files per control (CuratedEvidenceItem).
  • Progress summary: % implemented, % verified, domain-grouped gap analysis.
  • OCR + AI assessment kicked off on every evidence upload in background.

3.6 Compliance Plugins (CIS Benchmark Scanning)

  • Multi-runner: WinRM (Windows), SSH (Linux), AWS/Azure/Oracle APIs.
  • Encrypted per-tenant credentials (Fernet). Scope selection by asset.
  • CIS benchmarks: all current generations (Windows 7 to 11, Server 2008 to 2022, Ubuntu 20/22/24, Debian, RHEL, AlmaLinux, OracleLinux, Amazon Linux, Rocky, Cisco IOS/NX-OS, K8s).
  • Strict-matcher: BenchmarkOsMapping table picks the right plugin set per asset OS automatically.
  • Auto-create Evidence from scan results; auto-match Evidence ↔ FrameworkControl via benchmark_matcher.
AI: OS normalizer Strict matcher (regex) AI: benchmark-OS mapping suggester (anti-hallucination)

3.7 Framework Upload & Parsing

  • PDF ingest pipeline: extract_pages → parse_fields → classify → gen_check → benchmark_supersession.
  • Field extraction: original_reference, title, description, control_level.
  • Supersession resolution for CIS benchmark version conflicts (v4 → v5 → v6).

3.8 NCA (Saudi National Cybersecurity Authority) Templates

  • Templated intake: NcaRiskEntry, NcaVulnEntry.
  • NCA-specific fields preserved verbatim on bridged Risk/Vulnerability (template_fields JSON).
  • Status bridge: NCA {OPEN / IN PROGRESS / ON HOLD / RESOLVED} → general {open / in_progress / resolved}.
  • Idempotent sync. re-importing the same NCA file updates the existing bridged record.
  • Five routers: nca_risk_router, nca_vuln_router, nca_templates_router, nca_container_router, nca_kpi_router.

4. Evidence Library

3 sub-modules · OCR + AI Quick-Assess · 16 evidence types

4.1 Evidence Library & Versioning

  • States: draft → pending_review → approved → rejected; stale-flag once past validity_period_days.
  • 16 evidence types: policy, procedure, log, report, screenshot, record, configuration, certificate, contract, attestation, test_results, register, inventory, plan, matrix, training.
  • Ownership chain: uploader (uploaded_by) ≠ owner (designated keeper); review/approval lifecycle (submitted_by → reviewed_by → approved_by).
  • OCR pipeline: pending → processing → completed/failed; content_summary, quality_score.
  • Expiry management: collection_date + validity_period_days → expiry_date; recertification_date; stale flag for dashboard.
  • Version history: EvidenceVersion (number, changes, created_by) audit trail of file replacements.
  • Encryption at rest: Fernet per-tenant keys.

4.2 Evidence Quick-Assess (AI)

  • AI semantic matching of evidence content to control requirements.
  • Matched-text snippet extraction (literal quotes from evidence body).
  • Similarity_score + confidence_score (0 to 100).
  • Locking mechanism: evidence owner can lock mappings to prevent AI drift on re-assessment.
  • Bulk endpoint: /evidence/*/assess-bulk.
AI: semantic match AI: snippet extraction Bulk assess

4.3 Evidence Cross-Links (the glue)

  • EvidenceControlMapping. Evidence ↔ NormalizedControl / FrameworkControl / ParsedFrameworkControl (with confidence_score, coverage_type: full / partial / supporting / not_applicable).
  • RiskEvidenceLink, AssetEvidenceLink, EvidenceIncidentLink, AuditPackageEvidence.
  • RiskMitigationActionEvidence, AttestationRequest.evidence_id, IssueEvidenceLink.
  • Reverse-lookup endpoints: /evidence/{id}/risks, /evidence/{id}/assets, /evidence/{id}/control-mappings.

5. IT Assets

4 sub-modules · ISO 27005 criticality scoring · Connect Wizard

5.1 IT Asset Inventory

  • Attributes: name, asset_type (application / infrastructure / data / cloud / third_party), host_name, IP, status.
  • Ownership chain: primary_owner_id, secondary_owner_id, business_owner_id, escalation_contact_id, owning_team_id (FK to Teams).
  • Exposure metadata: internet_facing, network_segment (dmz / prod-app-tier / …), data_classification, business_function, compliance_scope (["PCI-DSS","HIPAA",…]).
  • CIA ratings: confidentiality / integrity / availability (1 to 5) → derived criticality_score (0.0 to 10.0 ISO 27005).
  • Lifecycle state machine: planned → active → maintenance → decommissioned → retired; replacement_asset_id (self-FK).
  • Last-seen tracking: last_seen_at + last_seen_source (nessus / manual / azure_defender / …).
  • OS fingerprinting: os_family, os_version, os_normalized, os_build, os_edition (auto-populated by Connect Wizard).

5.2 Asset Criticality Assessments (Bank Template Parity)

  • ISCA. Information System Criticality Assessment (apps, middleware, DBs).
  • IACA. Infrastructure Asset Criticality Assessment (network, storage, physical).
  • Server-computed scoring bands → criticality level (low / medium / high / critical).
  • Multi-tier approval: business owner → CISO (permission: assets:criticality_assessments:approve_ciso).
  • Evidence attachments, activity audit trail, threaded comments.

5.3 Asset Auto-Classification & Control Recommender

  • Auto-classify: regex-driven asset_type inference from name + vendor + network_segment.
  • Criticality formula: ISO 27005 base (CIA) + internet_facing (+2.5) + data_classification (+1.0 to 1.5) + business_function (+1.5), clamped [0,10].
  • Mapping recommender. pure regex (no LLM), 45+ signals per asset_type. Confidence buckets: ≥8 high, ≥4 medium, ≥1 low. Operator one-clicks to accept and link.
  • Manual override: criticality_manual_override flag + criticality_override_reason audit field.
Regex (no LLM) AI fallback: anti-hallucination

5.4 Connect Wizard (Agentless OS Probing)

  • One-liner customer onboarding: issue token → PowerShell / bash one-liner → handshake within 60-min TTL window.
  • Security: JWT token (tenant_id + nonce), per-machine random agent password (never echoed).
  • Probes: WinRM (Get-CimInstance), SSH (uname / apt list), AWS boto3. auto-detects OS, normalises, creates asset.
  • Preflight: auth_failed, network_unreachable, ssl_error hints to UI before scan.
  • Credentials encrypted via Fernet (per-tenant key).

6. Vulnerability Management

3 sub-modules · KEV + EPSS enrichment · NCA Saudi template

6.1 Vulnerability Register

  • Lifecycle: open → in_progress → resolved / accepted / false_positive.
  • Per-vulnerability: title, severity (critical / high / medium / low / info), CVSS_score, CVE_id, CWE_id, affected_component / host / port / URL.
  • Threat-intel enrichment: EPSS score + percentile, KEV flag (CISA Known Exploited Vulnerabilities list), NVD pub/mod dates, exploit references, GitHub PoC count.
  • Composite priority formula: 0.4 × CVSS + 0.3 × (EPSS × 10) + 0.2 × (KEV ? 10 : 0) + 0.1 × asset_criticality.
  • Exception workflow: is_exception, exception_reason, exception_expiry, exception_approved_by.
  • Workflow template binding: workflow_template_id, current_state_id.
  • SLA tracking: per-severity remediation deadlines, overdue highlighting, MTTR per team, aging buckets (0 to 30d / 31 to 60d / 61 to 90d / 90+).

6.2 Vulnerability Reports & Scanner Ingestion

  • VulnerabilityReport with type (vulnerability_scan / penetration_test / code_review / configuration_audit) and scan_tool (nessus / qualys / burp / owasp_zap / manual).
  • Bulk import with auto-dedup, asset auto-link, severity normalisation.
  • Lifecycle: uploaded → parsing → parsed → analyzed → closed.
  • Patch correlation: which patches close which vulns.

6.3 NCA Saudi Vulnerability Template

  • NCA-specific fields preserved on bridged Vulnerability (template_fields JSON): vendor_link, cve_score, affected_technology, threat_analysis, threat_severity, risk_likelihood, risk_severity, first_observation_date, due_date, resolution_date, comments, vuln_identifier.
  • Idempotent backing. re-importing the same NCA spreadsheet updates the same Vulnerability row.
  • Bridged detail page surfaces NCA fields in a read-only panel.

10. Administration · Auth · Identity · RBAC

7 sub-modules · 140+ permissions · 4 SSO types

10.1 Users & Identity

  • GRCUser (global) + TenantUser (bridge with is_primary flag) supports user belonging to multiple tenants.
  • Password hashing (bcrypt). Session tokens (HS256, 24h TTL, 6h refresh threshold).
  • Email domain filtering (personal-domain block-list).
  • Per-tenant IdentityProviderConfig with entra_directory_id.
  • SSO reconciliation: Entra group → role mapping (source='sso' field protects from manual overwrites).

10.2 Roles & Permissions (RBAC)

  • Role system roles (is_system_role=True) plus tenant-scoped custom roles.
  • Permission table indexed on (resource, action). 140+ permissions across all modules.
  • Custom roles with granular permission picker.
  • Role assignment scoped per tenant + optional BusinessUnit.
  • Manual vs SSO-sourced assignments tracked separately (source field).
resource:action grid tenant + BU scoping SSO reconciliation

10.3 Tenants & Multi-Tenancy

  • Slug-based subdomain routing (e.g. acme.localhost).
  • Organisation metadata: legal_entity, industry, regulatory_scope, geography, company_size.
  • Per-tenant settings JSON blob.
  • BusinessUnit hierarchy (parent_id self-FK) for resource scoping.
  • Database-per-tenant isolation (separate Postgres DB per tenant + master registry DB).

10.4 Password & Session Policy

  • PasswordSessionPolicy single row per tenant.
  • Configurable complexity, expiry, history, lockout threshold, idle timeout.
  • MFA: optional / required.

10.5 Audit Trail (Tamper-Evident)

  • AuditLog captures every CRUD: actor, timestamp, resource_type, resource_id, IP, before/after diff (JSON).
  • Plain-English action summaries auto-generated.
  • IntegrationAuditLog separately for integration connection events.
  • Indexed by (tenant_id, timestamp) for efficient queries.
  • CSV/JSON export to satisfy auditor requests.

10.6 SSO & Identity Providers

  • Microsoft Entra ID / Azure AD. multi-tenant via entra_directory_id, OAuth2, group → role mapping.
  • SAML 2.0. generic SAML provider support.
  • OIDC. OpenID Connect.
  • LDAP / Active Directory bind. bind-and-search for legacy environments.

19. Cross-Cutting Concerns

Multi-tenancy · Audit · RBAC · Encryption · Async

19.1 Multi-Tenancy Isolation

  • Pattern: database-per-tenant (separate Postgres database per customer) + master registry DB.
  • Tenant resolution from subdomain or header on every request.
  • All routers enforce require_tenant_permission() + tenant_id filtering.
  • Cookie domain configurable via AUTH_COOKIE_DOMAIN env.

19.2 Audit Trail Coverage

  • Logged entities: Risks, Evidence, Vulnerabilities, Frameworks, Controls, Governance docs, Compliance items, Assets, Integrations, Workflows, Users, Chat sessions.
  • AuditLog.changes JSON captures before/after. never overwritten.
  • Timestamps UTC with millisecond precision, indexed (tenant_id, timestamp).

19.3 Encryption & Secrets

  • Integration credentials: Fernet-encrypted encrypted_credentials blob.
  • Cloud connector creds: AES via CONNECTOR_MASTER_KEY.
  • OAuth2 tokens: separate encrypted oauth_tokens field.
  • Per-tenant Evidence file encryption with Fernet.
  • CIS benchmark scanner creds: per-field encryption (decrypt on demand).

19.4 Async Task Management

  • Framework: Celery for long-running ops (gap analysis, document parsing, framework upload, vulnerability sync, embedding pipeline).
  • /tasks/{task_id} polls status: PENDING / STARTED / SUCCESS / FAILURE / REVOKED.
  • Tenant isolation: task args[0] = tenant_slug; validation in _payload_tenant().

19.5 Permission Matrix

  • Permission = (resource, action). resources: risks, controls, evidence, workflows, integrations, vendors, issues, tasks, projects, audit_logs, admin, governance, assets, vulnerabilities, frameworks, …
  • Actions: view / create / update / delete / approve / verify / publish / execute / manage.
  • Tenant + optional business-unit scoping on every role assignment.
  • UI hides forbidden buttons; backend denies forbidden requests.
