Why database-per-tenant

Strongest isolation of the three multi-tenancy patterns. A missed tenant_id filter can't leak data because there is no shared table — each tenant is a separate database resolved per request from the registry. On managed Postgres it's one instance with N databases, so cost matches schema-per-tenant.

Hardened, not a prototype

RBAC (140+ permissions), audit log with diffs, SSO (SAML/OIDC), evidence encryption at rest (per-tenant keys), configurable password policy, per-tenant backups, Kubernetes health checks, Sentry-compatible error tracking.

Connectors & AI layer

Real-world data flows in through three connector types and normalizes into the same asset / vulnerability model. AI is used in exactly three places — deliberately scoped so it pays for itself.

Agentless

Platform pushes a probe over WinRM / SSH and parses the response. Best for one-off scans and on-demand audits.

Agents

Small Python collector on the box pulls jobs and pushes results — for fleets behind NAT and continuous scanning.

Cloud & external

AWS Inspector, Azure Defender, GCP SCC, plus ServiceNow / Splunk / Teams. All normalize into one model.

AI — three places, deliberately scoped

ComplyChat

Natural-language Q&A compiled to SQL via tool-use. "Show critical vulns on Payments-team assets with no compensating control." Read-only by default.

Asset auto-classify

Reads OS probe data, tags family / version / edition, then a CIS strict-matcher picks the ruleset. Deterministic — no LLM cost.

Mapping recommender

Scores every framework control against an asset across 8 weighted signals. Pure regex, no LLM. One click to link suggested controls.
