### Column Guidance

| Column | What to enter |
|---|---|
| NC ID | Enter a unique identifier for the nonconformity, using a consistent format such as NC-YYYY-###. |
| Date Identified | Enter the date the nonconformity was detected in YYYY-MM-DD format. |
| Identified By | Enter the name and role of the person who identified or reported the nonconformity. |
| Source of Nonconformity | Select or enter the source, such as Internal Audit, External Audit, Management Review, Incident Review, Supplier Review, Control Testing, Risk Assessment, Process Monitoring, Customer Complaint, or Other. |
| Audit / Assessment Reference | Enter the audit, assessment, review, incident, ticket, or report reference where the nonconformity was identified; enter N/A if not applicable. |
| ISO/IEC 27001:2022 Clause or Annex A Control Reference | Enter the applicable ISO/IEC 27001:2022 clause or Annex A control reference, for example Cl. 6.1.2, Cl. 8.1, Cl. 9.2, Cl. 10.2, A.5.15, or A.8.15. |
| Process / Asset / Location Affected | Enter the ISMS process, business area, information asset, system, site, or supplier affected by the nonconformity. |
| Nonconformity Statement | Enter a concise factual statement of the requirement not met, the observed condition, and why it is a nonconformity. |
| Objective Evidence | Enter the evidence supporting the nonconformity, such as document names, screenshots, logs, audit samples, interview notes, ticket IDs, or record references. |
| Severity | Select one value: Critical, Major, Minor, or Opportunity for Improvement, according to the organisation’s nonconformity classification criteria. |
| Immediate Correction / Containment Taken | Enter the immediate action taken to correct the detected issue or contain its impact; enter Pending if not yet completed. |
| Correction / Containment Completion Date | Enter the date immediate correction or containment was completed in YYYY-MM-DD format; leave blank until completed. |
| Consequences / Impact Addressed | Describe how actual or potential consequences were dealt with, including security, operational, legal, contractual, customer, or risk impacts. |
| Root Cause Analysis Method | Enter the method used to determine cause, such as 5 Whys, Fishbone/Ishikawa, Fault Tree Analysis, Process Review, Human Factors Review, or Other. |
| Root Cause Description | Enter the underlying cause or causes that allowed the nonconformity to occur; do not repeat only the symptom. |
| Similar Nonconformities Exist or Could Occur Elsewhere | Select one value: Yes, No, or Not Yet Determined, based on whether similar issues exist or could reasonably occur in other processes, systems, sites, suppliers, or controls. |
| Similar / Potential Areas Reviewed | List the processes, systems, controls, locations, suppliers, or records reviewed to determine whether similar nonconformities exist or could occur. |
| Corrective Action Required | Select Yes or No; select Yes when action is needed to eliminate the root cause and prevent recurrence or occurrence elsewhere. |
| Corrective Action Plan | Enter the planned action or actions to eliminate the root cause, including deliverables and expected outcome. |
| Action Owner | Enter the accountable owner responsible for implementing the corrective action, including name and role. |
| Target Completion Date | Enter the planned completion date for the corrective action in YYYY-MM-DD format. |
| Actual Completion Date | Enter the date the corrective action was fully implemented in YYYY-MM-DD format; leave blank until complete. |
| Implementation Evidence Reference | Enter references to evidence proving implementation, such as change record IDs, updated procedures, training records, configuration evidence, screenshots, test results, or ticket links. |
| Effectiveness Verification Method | Describe how the organisation will verify the corrective action was effective, such as re-audit, sample testing, control test, KPI review, log review, interview, or evidence inspection. |
| Effectiveness Verified By | Enter the name and role of the person verifying effectiveness; this should be independent of the action owner where practicable. |
| Effectiveness Verification Date | Enter the date effectiveness was verified in YYYY-MM-DD format; leave blank until verification is completed. |
| Effectiveness Result | Select one value: Effective, Ineffective, Partially Effective, or Pending Verification. |
| Further Action Required | Enter Yes or No; if Yes, reference the additional action, linked NC ID, or new corrective action required. |
| ISMS Changes Required | Enter Yes or No to indicate whether changes to the ISMS are required, such as policy, process, risk assessment, Statement of Applicability, control design, objectives, training, or monitoring changes. |
| ISMS Change Reference | Enter the reference to the related ISMS change record, document update, risk treatment update, SoA change, or management review action; enter N/A if no ISMS change is required. |
| Status | Select one value: Open, Contained, Root Cause Analysis, Corrective Action In Progress, Awaiting Verification, Closed, or Overdue. |
| Closure Approved By | Enter the name and role of the authorised person approving closure of the nonconformity. |
| Closure Date | Enter the approved closure date in YYYY-MM-DD format; leave blank until closure is approved. |
| Record Retention Reference | Enter the location or reference where documented information is retained, such as GRC record ID, SharePoint path, audit tool link, ticket ID, or document repository reference. |

### Maintenance

The ISMS Manager owns this register, with updates made whenever a nonconformity is raised, corrected, actioned, verified, or closed, and reviewed at least monthly and during management review. Source data is drawn from the GRC platform, audit reports, incident/problem records, risk treatment actions, control testing results, supplier reviews, and document/change management systems.
